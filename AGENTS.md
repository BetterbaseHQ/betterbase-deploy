# AGENTS.md

Guidance for AI coding agents working in this repository.

## Overview

Production self-hosting deployment for the Betterbase platform. Pulls prebuilt service images from GHCR and wires them together with Docker Compose behind a rate-limiting Caddy reverse proxy. Services themselves are developed in the [BetterbaseHQ](https://github.com/BetterbaseHQ) repos (`betterbase-accounts`, `betterbase-sync`) — this repo only deploys them.

| Service | Image | Notes |
|---|---|---|
| `caddy` | built from `./caddy` | Caddy 2 + `caddy-ratelimit` plugin; config in `caddy/Caddyfile` |
| `accounts` | `ghcr.io/betterbasehq/betterbase-accounts:latest` | OPAQUE + OAuth 2.0, port 5377 (internal) |
| `sync` | `ghcr.io/betterbasehq/betterbase-sync:latest` | Encrypted blob sync, port 5379 (internal) |
| `samples` | `ghcr.io/betterbasehq/betterbase-examples:latest` | Hosted example apps, port 8080 (internal); launchpad at `/`, apps at `/<app>/` |
| `cap` | `tiago2/cap` (digest-pinned) | Proof-of-work CAPTCHA; upstream has no version tags, so bumps are deliberate |
| `valkey` | `valkey/valkey:9-alpine` | Redis-compatible backing store for CAP |
| `accounts-db`, `sync-db` | `postgres:18-alpine` | One database per service |

Caddy publishes the only host ports: 80/443 plus `${ACCOUNTS_PORT:-5377}`/`${SYNC_PORT:-5379}`/`${SAMPLES_PORT:-5380}` (the latter three are dead in TLS mode — nothing in the container listens on them). Everything else is internal.

## Commands

```bash
./setup.sh              # Create .env (random keys), generate OPAQUE keys, provision CAP
./setup.sh --domain d   # Same, but serves https://accounts.d + https://sync.d + https://samples.d (Let's Encrypt)
docker compose up -d    # Start the stack
docker compose ps       # Health status
docker compose logs -f  # Tail logs
docker compose down     # Stop (add -v to wipe data volumes)
```

`setup.sh` is idempotent — it skips any credential already present in `.env`.

The Caddyfile is bind-mounted into the container (never baked into the image): after editing `caddy/Caddyfile`, apply with `docker compose restart caddy`. Rebuild only when the Caddy binary/plugins change.

## Configuration

`.env.example` documents every variable. Required values are generated by `setup.sh`: `OPAQUE_SERVER_SETUP` (via the accounts image's `keygen` binary), `IDENTITY_HASH_KEY`, `CAP_ADMIN_KEY`, CAP site credentials (provisioned via CAP's admin API, using `jq`), and one `<APP>_CLIENT_ID` per sample app (OAuth clients created via the accounts image's `oauth-client` binary — idempotent, reuses existing clients by name).

## Conventions

- Keep `docker-compose.yml` service definitions in sync with the production base in `betterbase-dev/docker-compose.yml` — especially the CAP digest pin, healthchecks (accounts/sync use `curl`, caddy/samples use busybox `wget`), and env var names, which must match what the services actually read (see each service repo's `AGENTS.md`).
- The samples image (`betterbase-examples` repo) serves all example apps path-based from one container: launchpad at `/`, apps at `/<app>/`. Deployment-specific config (accounts domain, OAuth client IDs, enabled apps) is injected at container start by its entrypoint (`config.js` + script-tag injection) — the image itself is deployment-agnostic. `setup.sh` must keep the redirect URIs it registers in sync with the samples origin (`SAMPLES_SITE` in TLS mode, `http://localhost:${SAMPLES_PORT}` otherwise). setup.sh targets bash 3.2 (macOS): no `${var^^}`, and empty arrays need `${arr[@]+"${arr[@]}"}` under `set -u`.
- The Caddyfile is mirrored from `betterbase-dev/caddy/Caddyfile`; rate-limit tiers are documented there and in each service's `docs/RATE-LIMITING.md`. Site addresses are env-driven (`{$ACCOUNTS_SITE::5377}` / `{$SYNC_SITE::5379}` / `{$SAMPLES_SITE::5380}`): unset or `:PORT` serves plain HTTP on that port; a hostname serves automatic HTTPS on 443 with ACME. Compose must never pass these as empty strings — Caddy's default only applies when the variable is unset, and an empty site address is a parse error. `setup.sh --domain` writes `ACCOUNTS_SITE`/`SYNC_SITE`/`SAMPLES_SITE`/`SAMPLES_ACCOUNTS_DOMAIN`/`ACME_EMAIL` into `.env`.
- Image tags: our own GHCR images track `:latest` — including the keygen image in `setup.sh`, which shares the accounts tag so keygen and server always agree on the OPAQUE format. Deliberate version pins come once things stabilize. Third-party images must be version-pinned at minimum, and digest-pinned when only a floating tag exists (see `cap`).
- Service images are published for `linux/amd64` and `linux/arm64`; on Apple Silicon run `--platform linux/arm64` explicitly if you see the amd64-emulation warning (stale local images predate the multi-arch builds).

## Verification

```bash
cp .env.example .env    # dummy values are fine for a config render
docker compose config   # must validate
```

Full-stack check: run `./setup.sh` then `docker compose up -d --wait` — every service must report healthy.
